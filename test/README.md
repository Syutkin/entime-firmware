# Тесты прошивки

Host-тесты проверяют ожидаемое поведение прошивки: штатную работу, переходы
состояний, пограничные значения и обработку отказов. Выполняются текущие исходники
из `src/`; оборудование заменяется моделями. Известные нарушения ожиданий имеют
маркеры `XFAIL`, перечисленные в [таблице открытых замечаний](#открытые-замечания).

## Запуск

Нужны Python 3.9+, компилятор C++17 (`g++` по умолчанию) и установленные зависимости
окружения прошивки. ArduinoJson и MicroNMEA берутся из той же `.pio/libdeps`, что
и при сборке прошивки. Для первоначальной установки нужен PlatformIO и сеть:

```bash
pio pkg install --environment rymcu-esp32-s3-devkitc-1
```

После установки host-тесты работают без сети и ESP32. Команды выполняются из корня
репозитория:

```bash
python3 test/run_host_tests.py
python3 test/run_host_tests.py --sanitize
python3 test/run_host_tests.py --sanitize --strict
```

| Параметр | Назначение |
| --- | --- |
| `--sanitize` | Включает UndefinedBehaviorSanitizer |
| `--strict` | Считает известные дефекты `XFAIL` ошибками запуска |
| `--suite TEXT` | Отбирает пути наборов до компиляции |
| `--filter TEXT` | Отбирает имена отдельных сценариев |
| `--environment NAME` | Выбирает зависимости окружения PlatformIO; по умолчанию `rymcu-esp32-s3-devkitc-1` |
| `--libdeps-dir PATH` | Путь к общему каталогу зависимостей, если в PlatformIO изменён `libdeps_dir` |
| `CXX` | Выбирает компилятор, например `CXX=clang++` |

Примеры запуска по подсистемам:

```bash
python3 test/run_host_tests.py --sanitize --suite host/timing/
python3 test/run_host_tests.py --sanitize --suite host/events/
python3 test/run_host_tests.py --sanitize --suite host/settings/
python3 test/run_host_tests.py --sanitize --suite host/commands/
python3 test/run_host_tests.py --sanitize --suite host/gps/
python3 test/run_host_tests.py --sanitize --suite host/rtc/
python3 test/run_host_tests.py --sanitize --suite host/touch/
python3 test/run_host_tests.py --sanitize --suite host/battery/
```

Для одного набора или сценария можно уточнить фильтр:

```bash
python3 test/run_host_tests.py --sanitize --suite event_pipeline
python3 test/run_host_tests.py --sanitize --suite host/gps/ --filter checksum
```

## Группы тестов

### Синхронизация времени

Основная логика выбора источника UTC, привязки PPS/SQW, дисциплины часов,
потери источников и восстановления находится в [host/timing/](host/timing/).

| Набор | Что проверяется |
| --- | --- |
| [time_sync_nominal_test.cpp](host/timing/time_sync_nominal_test.cpp) | Штатный запуск с GPS/RTC и без них, захват времени, стабильная работа, переключения источников, `auto_sync`, политики `auto`/`gps`/`rtc`, уведомления |
| [time_sync_boundary_test.cpp](host/timing/time_sync_boundary_test.cpp) | Границы свежести/фазы/окон обработки, календарь, rollover счётчиков и изменения настроек |
| [time_sync_test.cpp](host/timing/time_sync_test.cpp) | Регрессии привязки UTC, переходов и восстановления |
| [gps_utc_trust_test.cpp](host/timing/gps_utc_trust_test.cpp) | Доверие к UTC из NMEA и подтверждение номера секунды |
| [pps_isr_test.cpp](host/timing/pps_isr_test.cpp) | Настоящий PPS ISR, timestamp/счётчик, warmup, джиттер, пропуски, lock/relock, час импульсов |
| [rtc_sqw_isr_test.cpp](host/timing/rtc_sqw_isr_test.cpp) | Настоящий SQW ISR, warmup, периоды, таймаут, lock/relock, rollover и повторная инициализация |
| [rtc_sqw_recovery_test.cpp](host/timing/rtc_sqw_recovery_test.cpp) | SQW ISR вместе с синхронизацией: лишние/пропущенные фронты, задержки loop, повторные сбои и калиброванная фаза |
| [rtc_drift_test.cpp](host/timing/rtc_drift_test.cpp) | Час работы при дрейфе ESP ±100/±500 ppm, оба режима `auto_sync`, задержки обработки, сдвиги системных часов и GPS → RTC → GPS |
| [rtc_latency_test.cpp](host/timing/rtc_latency_test.cpp) | Задержки проверки/чтения RTC до 25 мс, первичная привязка, периодическая проверка и восстановление после просроченного чтения |
| [rtc_manual_correction_test.cpp](host/timing/rtc_manual_correction_test.cpp) | Явная установка RTC вперёд/назад, повторные записи, старые фронты, невалидная дата и цепочка NTP → RTC → UTC событий |
| [rtc_pps_schedule_test.cpp](host/timing/rtc_pps_schedule_test.cpp) | Запись RTC на следующем PPS, пропуск цели, перепланирование, отмена и rollover |
| [rtc_trust_loss_test.cpp](host/timing/rtc_trust_loss_test.cpp) | Потеря доверия к RTC при продолжающемся SQW: lost power, невалидная дата, holdover и восстановление |
| [sntp_test.cpp](host/timing/sntp_test.cpp) | Серверы и предусловия NTP, свежий ответ SNTP, запись RTC на границе секунды, таймауты и rollover `millis()` |

Основные границы:

| Область | Значения и сценарии |
| --- | --- |
| NMEA/PPS | Возраст начала NMEA 1 500 000 мкс и +1 мкс; timestamps из будущего; фаза ±990 000 мкс, значения снаружи окна и запрещённая зона около ±1 секунды |
| PPS/SQW | PPS interval guard 850 000–1 150 000 мкс; периоды ISR 800 000–1 200 000 мкс; значения на 1 мкс снаружи; rollover `UINT32_MAX → 0 → 1` |
| Потеря сигнала | PPS timeout 2,8 с, SQW timeout 1,5 с; GPS holdover 10 с и RTC holdover 30 с, точная граница и следующая микросекунда |
| Обработка RTC | Первичный SQW anchor при возрасте 50 000/50 001 мкс; обычное окно 900 000/900 001 мкс; переход чтения I²C в следующую секунду |
| Запись RTC по PPS | Окно 3 000 мкс, отказ при 3 001 мкс, исчезновение RTC или смена `auto_sync` перед записью |
| NTP | Ответ до, на и после deadline; окно начала секунды до 1 500 мкс включительно; следующий фронт при 1 501 мкс |

NTP deadlines имеют исключительную верхнюю границу: ответ/фронт ровно на deadline
не принимается. При rollover SQW-счётчика (около 136 лет при 1 Гц) фронт `0`
пропускается, следующий (`1`) читается штатно. Это проверяемые условия API.

В timing-наборах GPS, RTC/I²C и системные часы моделируются. Часть наборов задаёт
PPS/SQW-сигналы напрямую, а `pps_isr`, `rtc_sqw_isr`, `rtc_sqw_recovery`, `rtc_drift`,
`rtc_latency`, `rtc_manual_correction` и `rtc_trust_loss` выполняют настоящие ISR
соответствующего источника. Штатные состояния строятся через публичные
`time_sync_begin()`/`time_sync_update()`; отдельные исходные регрессии используют
внутренний anchor для подготовки уже работающего RTC.

первой метки в занятом single-slot ISR. В отдельных наборах форматирования и
BLE-доставки конвертация ESP → UTC задана моделью для изоляции этих частей.

### Настройки и NVS

| Набор | Что проверяется |
| --- | --- |
| [settings_persistence_test.cpp](host/settings/settings_persistence_test.cpp) | Сохранение с заводским/изменённым именем, перезапуск, неизменённые настройки без повторных записей, ошибки записи разных типов ключей и очистки, factory reset |
| [settings_validation_test.cpp](host/settings/settings_validation_test.cpp) | Типы/диапазоны JSON, частичное обновление с сохранением пропущенных полей, откат всех групп при поздней ошибке, явное сохранение, полный roundtrip, defaults для отсутствующих ключей и сброс невалидной конфигурации |

Выполняется настоящий `settings.cpp`. Модель NVS сохраняет значения между

ключа или очистке. Для проверки атомарности сравниваются все группы настроек,
включая исходный пароль, и содержимое хранилища.

В тестах parser результатом считается передача JSON модели роутера; в наборе
router выполняется настоящий маршрут до обработчика. HAL, результат NTP,
калибровочный wizard и API reset-таймера моделируются. Проверяются переданные
параметры, ответы и побочные действия; перезагрузка компьютера не выполняется.

Проверки логов охватывают BLE/Serial, `wifi`/`save_config`, экранированные
ключи/значения, фрагменты, вложенные массивы, пустой пароль и повреждённый ввод.
В логах ожидается `***`, обработчик должен получить исходный пароль; остальные
поля команды сохраняются.

### GPS

[gps_driver_test.cpp](host/gps/gps_driver_test.cpp) выполняет настоящий
`gps.cpp` с MicroNMEA:

- Выключение, включение и повторный `begin`, обработка UART-фрагментов.
- Метки обработки `$` и завершения предложения, свежесть NMEA/UTC на deadline,
  устаревание и timestamps из будущего, повтор одной UTC-секунды.
- Потеря/возврат fix, старая дата, неверный checksum, восстановление после шума,
  уведомления только при изменении состояния и удаление callbacks.
- GSV: раздельные talker/PRN, обновление и ёмкость списка, замена старейшей записи,
  возраст спутников, ограничения выходного массива и пустой SNR.

UART заменён очередью байтов. GPS timestamps соответствуют моменту обработки
байта в `update()`, как и в прошивке; электрическое время прихода байта не измеряется.

### RTC

[rtc_driver_test.cpp](host/rtc/rtc_driver_test.cpp) выполняет настоящий
`rtc.cpp`:

- Недоступный RTC, повтор после отказа и идемпотентность `begin`, отдельная I²C-шина,
  настройка SQW, lost power и минимально доверенная дата.
- Три перегрузки установки времени, високосная дата, повторная коррекция и
  обновление `lastSyncUs`.
- Знаковый aging-регистр, шаг 0,1 ppm, округление и насыщение до диапазона int8,
  NACK/короткое чтение и сохранение выходного значения при отказе.
- Чтение температуры с отрицательной и дробной частью.

Моделируются RTClib/DS3231 и TwoWire; доступ к aging-регистру проходит через
реальные методы драйвера. Частота SQW и физическая точность DS3231 требуют
проверки на оборудовании. Взаимодействие RTC с синхронизацией описано в первой группе.

`config_command_test.cpp`.

### Батарея

[battery_driver_test.cpp](host/battery/battery_driver_test.cpp) выполняет
настоящий `ina226.cpp` с моделью API сенсора:

- Отказ обнаружения, калибровки или конфигурации; повтор и идемпотентность `begin`;
  bootstrap timeout и восстановление.
- Настоящий GPIO ISR DATA_READY, проверка готовности преобразования, объединение
  нескольких IRQ в одно чтение и отсутствие чтения без IRQ.
- Ошибки чтения, NaN/Inf в напряжении/токе/мощности, сброс измерений и восстановление.
- Проценты и уровни заряда, ограничения 0–100%, все границы гистерезиса и соседние
  представимые float, устойчивость к шуму, порог зарядки −20 мА.
- Подавление одинаковых уведомлений при разрядке, уведомление об изменении процента,
  удаление callback и повторные уведомления при зарядке для анимации.

Повторные callbacks при зарядке — штатное поведение из
[TOUCH_UI.md](../doc/TOUCH_UI.md), необходимое для смены кадров иконки.

## Устройство стенда и ограничения

```text
test/
  run_host_tests.py        # обнаружение наборов, сборка и отчёт
  host/
    timing/               # синхронизация, PPS/SQW и NTP
    events/               # захват события, метки, пакеты и BLE-доставка
    settings/             # валидация, атомарность и сохранение NVS
    commands/             # parser, router и обработчики Serial/BLE
    gps/                  # GPS-драйвер и NMEA
    rtc/                  # RTC-драйвер и aging-калибровка
    touch/                # автомат касаний и calibration flow
    battery/              # INA226 и состояние батареи
    support/
      application/        # общие часы, stream, окружение команд и pipeline
      test_runner.h       # выполнение отдельного сценария
      gpio_fixture.h      # окружение GPIO/ISR
      time_sync_fixture.h # окружение синхронизации
    stubs/
      base/               # GPIO, часы и модели timing-наборов
      application/        # HAL, NVS, BLE и TFT для составных сценариев
      drivers/            # UART, TwoWire, DS3231 и INA226 API
```

Сборка выполняется во временной папке, удаляемой после запуска. Каждый сценарий
запускается отдельным процессом, поэтому статическое состояние прошивки между
тестами не переносится. Системные часы компьютера не изменяются. Границы календаря
и ожидаемые UTC заданы независимо от часов, которые дисциплинирует прошивка.

Проверяются программные переходы и обработка результатов API. Радиоканал,
доставка BLE-уведомления клиентскому приложению, реальные flash/I²C, электрические
характеристики, аппаратные задержки и параллельные задачи ESP32 не моделируются.
NTP не выполняет реальных DNS/UDP-запросов. RTClib-модель реализует нужные стенду
операции с календарём и Unix time.

ArduinoJson и MicroNMEA используются непосредственно из
`.pio/libdeps/<environment>/`: заголовки ArduinoJson и заголовки/исходник MicroNMEA.
Зависимости задаются в `platformio.ini`; отдельных копий и ограничений версий для
тестов нет. При отсутствии нужных файлов runner останавливается до компиляции и
показывает команду установки. Наборы `timing/` внешних библиотек не требуют.

## Результаты запуска

| Статус | Значение |
| --- | --- |
| `PASS` | Ожидаемое поведение подтверждено |
| `FAIL` | Ожидание обычного теста нарушено |
| `XFAIL` | Известный дефект воспроизводится |
| `XPASS` | Тест известного дефекта прошёл; нужно проверить исправление и убрать маркер |
| `ERROR` | Ошибка сборки/стенда, таймаут, аварийное завершение или ошибка санитайзера |

Обычный запуск успешен при `PASS`/`XFAIL`; `FAIL`, `XPASS` и `ERROR` дают ненулевой
exit code. `--strict` дополнительно считает `XFAIL` ошибкой запуска.

## Открытые замечания

| ID | Подсистема | Нарушаемое ожидание |
| --- | --- | --- |
| AU001 | Настройки | Сохранённые Wi-Fi, роль/номер, калибровка и sync policy должны загружаться после перезапуска и при заводском имени устройства |
| AU002 | Доставка события | После исчерпания notify, частичной отправки или отсутствия подписки событие должно оставаться доступным для последующей полной доставки |
| AU003 | Синхронизация | Недоверенный RTC при непрерывном SQW не должен сохранять `RTC_OK` и бесконечно продлевать holdover |
| AU004 | NVS и команды | Ошибки записи/очистки должны доходить до вызывающего кода; неудачный reset не должен планировать reboot, а неудачное сохранение калибровки — применяться как успешное |
| AU005 | BLE RX | Новое подключение должно очищать RX и peek, сохраняя изоляцию команд клиентов |
| AU006 | Настройки touch | `save_config` должен немедленно применять включение, выключение и калибровку touch |
| AU008 | Парсер команд | Первая корректная команда после таймаута oversized-кадра должна обрабатываться, включая rollover `millis()` |
| AU009 | Валидация настроек | Типы и диапазоны JSON должны проверяться до преобразования: bool, группы, элементы калибровки, `timezone_offset_min=32768`, `sync.source=256` |
| AU010 | Factory reset | Отказ создания или запуска reset-таймера должен возвращать ошибку; сейчас `status: ok` отправляется до проверки таймера |
| AU011 | GPS fix | Неверный checksum не должен обновлять `lastFixUs` и сохранять `ACTIVE`; признак завершённой строки MicroNMEA сейчас принимается за успешную обработку |
| AU012 | GPS GSV | Последний спутник с пустым SNR должен присутствовать в списке со значением `-1` |

После исправления удалите строку замечания и его `known_issue` в таблице `kTests`;
сам тест сохраните как обычную регрессионную проверку. История исправленных
замечаний в этом списке не ведётся.

## Добавление тестов

Runner автоматически обнаруживает `host/**/*_test.cpp`. Добавляйте сценарии в
соответствующую группу; новые подсистемы оформляйте отдельными `*_test.cpp`.
Аппаратные проверки храните отдельно от host-наборов.

Каждый файл — самостоятельный исполняемый набор: `--list` выводит строки
`имя<TAB>идентификатор_дефекта`, запуск с именем выполняет один сценарий. Для обычного
теста идентификатор — `-`. Код `0` означает успех, `10` — нарушение ожидания;
остальные коды, сигналы и таймауты считаются ошибками стенда и не маскируются `XFAIL`.

Подготовку окружения выносите в `host/support/`, модели периферии — в нужный
профиль `host/stubs/`. Проверяйте ожидаемый результат и побочные действия независимо от
реализации. Если набору нужны дополнительные исходники или include paths,
добавьте их в таблицы `PRODUCTION_SOURCES`/`SUPPORT_SOURCES` в `run_host_tests.py`.
