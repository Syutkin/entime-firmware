# Тесты прошивки

Host-тесты выполняются на компьютере без ESP32, PlatformIO и скачивания библиотек.
Нужны Python 3.9+ и компилятор C++17 (`g++` по умолчанию).

Из корня репозитория:

```bash
python3 test/run_host_tests.py
python3 test/run_host_tests.py --sanitize
```

`--sanitize` включает UndefinedBehaviorSanitizer. Компилятор можно выбрать через
`CXX`, например `CXX=clang++ python3 test/run_host_tests.py --sanitize`.
Сборка выполняется во временной папке, которая удаляется после запуска.
Каждый сценарий запускается отдельным процессом: статическое состояние прошивки
не переносится между тестами. Запуск не меняет системные часы компьютера.

## Структура

```text
test/
  run_host_tests.py              # сборка, изоляция, отчёт и exit code
  host/
    stubs/                      # модели оборудования и системного времени
    support/                    # общий runner и подготовка окружения
    project/                    # NVS, команды, BLE-доставка и touch
      settings_persistence_test.cpp
      config_command_test.cpp
      command_parser_test.cpp
      ble_delivery_test.cpp
      stubs/                    # отдельные модели периферии для этих наборов
    timing/
      time_sync_nominal_test.cpp # штатные режимы и переходы
      time_sync_boundary_test.cpp # границы окон, rollover и смена настроек
      gps_utc_trust_test.cpp       # доверие к UTC
      time_sync_test.cpp         # исходные проверки и регрессии аудита
      pps_isr_test.cpp           # настоящие PPS ISR и lock
      rtc_sqw_isr_test.cpp       # настоящие SQW ISR и lock
      rtc_sqw_recovery_test.cpp  # SQW ISR вместе с синхронизацией времени
      rtc_drift_test.cpp         # дрейф ESP относительно настоящего SQW ISR
      rtc_latency_test.cpp       # задержки чтения RTC и возраст SQW после I2C
      rtc_manual_correction_test.cpp # явная установка RTC и NTP → RTC → UTC событий
      rtc_trust_loss_test.cpp    # потеря доверия RTC при продолжающемся SQW
      rtc_pps_schedule_test.cpp  # планирование записи RTC по PPS
      sntp_test.cpp              # NTP → системные часы → запись RTC
  vendor/ArduinoJson/            # настоящая JSON-библиотека для offline host-тестов
```

Runner обнаруживает `host/**/*_test.cpp`. Каждый такой файл — самостоятельный
исполняемый набор: `--list` выводит строки `имя<TAB>идентификатор_дефекта`,
запуск с именем выполняет один сценарий. Для обычного теста идентификатор — `-`.
Код возврата `0` означает успех, `10` — нарушение проверяемого ожидания;
остальные коды, сигналы, ошибки сборки и таймауты считаются ошибками стенда.

## Проверки синхронизации

Наборы включают текущие исходники `src/timing/` напрямую; сохранённых копий
реализации нет. Используются настоящие заголовки timing и `src/config.h`.
Подменены GPS, RTC, настройки, RTClib и вызовы системного времени.

В `time_sync_nominal_test.cpp` состояния создаются через публичные
`time_sync_begin()` / `time_sync_update()`, без прямой установки внутренних
anchor и guard-флагов. В boot-сценариях стенд либо подаёт свежий SQW при
инициализации, либо моделирует отсутствие фронтов и таймаут ожидания.

В исходных регрессиях `time_sync_test.cpp` для некоторых сценариев уже работающего
RTC напрямую создаётся внутренний anchor. Общая подготовка окружения вынесена
в `support/time_sync_fixture.h`. В обоих наборах `time_sync` lock PPS/SQW и
RTC-секунды задаются сценарием, чтобы независимо проверять логику переходов.

В `rtc_sqw_recovery_test.cpp` опция `HOST_REAL_RTC_SQW` подключает к настоящему
`time_sync.cpp` настоящий SQW driver. Прерывания вызываются через зарегистрированный
GPIO обработчик; lock не подменяется. Проверяются UTC событий и системные часы
при наблюдаемых/скрытых лишних фронтах, пропуске фронта, задержке loop, повторных
сбоях, смене `auto_sync` и GPS-калиброванной фазе SQW. Подменёнными остаются RTC
по I2C, GPS и системные вызовы времени.

`rtc_drift_test.cpp` также исполняет настоящий SQW driver. Независимые RTC-секунды
сравниваются с UTC событий и системных часов за час работы при дрейфе ESP
±100/±500 ppm, с включённым и выключенным `auto_sync`. Проверяются метки по обе
стороны последнего фронта, обработка с задержкой 850 мс, смена `auto_sync`,
отдельный сдвиг системных часов и GPS → RTC → GPS с калиброванной фазой SQW.

`rtc_latency_test.cpp` проверяет UTC событий и системных часов при задержке
проверки RTC от 0 до 25 мс и отдельной задержке чтения календарного времени.
Используется настоящий SQW driver: проверяются первичный захват, периодическая
проверка RTC, восстановление после лишнего фронта, GPS → RTC с известной фазой
и без неё, оба режима `auto_sync`. Проверяются также завершение I2C ровно на
границе окна 900 мс, на 1 мкс позже и в следующей секунде, сохранение прежнего
anchor при просроченном чтении и восстановление на своевременных фронтах.

`rtc_manual_correction_test.cpp` проверяет явную установку RTC вперёд и назад
на секунду, минуту и сутки, повторные записи, оба режима `auto_sync`, сохранение
системных часов, старые SQW-фронты, смену GPS-калиброванной фазы, потерю SQW,
недопустимую дату и восстановление RTC после потери питания. Подключены настоящие
`time_sync.cpp`, SQW driver и `sntp.cpp`: проверяется цепочка ответа SNTP,
записи RTC и обновления UTC событий, а также таймаут без записи. Подменены
сеть, системные часы и RTC по I2C; командный JSON-обработчик не исполняется.
Проверяется и сохранение защиты от чтения соседней секунды без явной записи RTC.

Отдельные `pps_isr_test.cpp` и `rtc_sqw_isr_test.cpp` исполняют настоящие ISR и
алгоритмы lock. Стенд вызывает обработчики, зарегистрированные настоящим кодом
через `attachInterrupt()`, и управляет временем GPIO-фронтов. Электрические
характеристики, аппаратные задержки и многопоточность ESP32 не моделируются.

`sntp_test.cpp` исполняет настоящий `sntp.cpp`, подменяя WiFi и API SNTP. Стенд
моделирует ответ сервера и системные часы, проверяет UTC и окно записи RTC.
Реальных DNS/UDP-запросов и сети нет. Модель RTClib поддерживает только нужные
тестируемому коду операции с календарной датой и Unix time.

## Штатные сценарии

| Область | Что проверяется |
| --- | --- |
| Отсутствие источников | Нет GPS, нет RTC, нет обоих; HAL готов, но PPS/SQW не приходят; NMEA без PPS; PPS без доступной UTC-секунды |
| Boot RTC | Доверенное время с SQW и без него, `auto_sync` включён/выключен; lost power; дата до 2020; загрузка часов UI без разрешения меток событий; истечение boot holdover |
| Захват GPS | Ожидание PPS lock; получение UTC при неустановленных системных часах; работа без RTC и с RTC после потери питания; NMEA до/после PPS |
| Захват RTC | Ожидание SQW lock; отказ от недоверенного RTC; независимый anchor при `auto_sync=false`; сохранение RTC-режима при наличии только NMEA |
| UTC событий | Конвертация до/после PPS, повторные вызовы loop, час непрерывной GPS-синхронизации, границы минуты/суток/года и вход в високосный день |
| Дисциплина часов | Поправка системных часов в обе стороны, игнорирование микроджиттера, периодическое обновление; включение/выключение `auto_sync` на ходу |
| Дисциплина RTC | Запись на следующем PPS, пропуск цели/фронта, перепланирование и rollover, отмена при потере PPS, восстановление доверия RTC после lost power, отсутствие записи при degraded GPS и `auto_sync=false` |
| Потеря GPS | Потеря/устаревание NMEA, сохранение времени по PPS, возвращение NMEA; короткая/длинная потеря PPS; граница holdover ровно 10 секунд и следующая микросекунда |
| Потеря RTC SQW | Короткая/длинная потеря lock, восстановление; граница holdover ровно 30 секунд и следующая микросекунда |
| Переключение источников | RTC → GPS, GPS → RTC; SQW на UTC-фазе и со сдвигом +354/−200 мс; ожидание SQW warmup; десять циклов GPS ↔ RTC; потеря обоих источников и восстановление GPS |
| Политика источника | `auto`, `gps` с RTC fallback, `rtc`; игнорирование GPS в RTC-only; переход в RTC-only с RTC и без него, возврат в auto |
| Уведомления | Первоначальное состояние, последовательность переходов, отсутствие повторных callback при неизменном состоянии, удаление callback |
| Настоящий PPS ISR | Захват timestamp/счётчика; warmup; отсутствие ложного lock от polling/быстрых импульсов; джиттер; пропуск одного PPS; граница таймаута 2,8 с; relock; час стабильных импульсов |
| Настоящий SQW ISR | Захват timestamp/счётчика; три полных периода до lock; polling/быстрые импульсы; джиттер; граница таймаута 1,5 с; relock; час стабильных импульсов; повторная инициализация |
| NTP | Один/два/три сервера, пустой второй сервер, отсутствие WiFi/RTC/основного сервера, сброс старого статуса COMPLETED, ожидание новой синхронизации, запись UTC на границе секунды, оба таймаута, необязательный duration, переполнение `millis()` |

Границы календаря заданы фиксированными UTC-секундами. Проверки ошибок времени
сравнивают результат с независимой ожидаемой UTC, а не только с системными часами,
которые тестируемый код сам может менять.

## Пограничные сценарии

| Граница | Что проверяется |
| --- | --- |
| Возраст NMEA | Начало предложения ровно 1 500 000 мкс назад и на 1 мкс старше при ещё свежем UTC completion; timestamp начала/завершения из будущего |
| Фаза NMEA/PPS | Нулевой delta, ±990 000 мкс включительно, ±990 001 мкс снаружи окна, ±995 000 мкс и ровно ±1 секунда в запрещённой зоне |
| PPS interval guard | 850 000/1 150 000 мкс включительно, отклонение ещё на 1 мкс; пропущенные периоды; неверный интервал перед новым baseline и длинный разрыв; повторный timestamp с изменённым счётчиком |
| Настоящие PPS/SQW lock | Периоды ровно 800 000 и 1 200 000 мкс, а также по 1 мкс за допустимыми пределами |
| Переполнение счётчиков | Raw PPS через `UINT32_MAX → 0 → 1`, raw SQW после rollover; GPS UTC и RTC cached anchor при rollover; отложенная запись RTC с целевым PPS counter `0` |
| Возраст SQW | Первичный anchor при 50 000/50 001 мкс; обычное окно 900 000/900 001 мкс после warmup; восстановление на следующем своевременном фронте |
| Окно записи RTC по PPS | 3 000 мкс включительно и отказ при 3 001 мкс с перепланированием записи |
| Изменения перед записью | Исчезновение и возвращение RTC между планированием и целевым PPS; выключение и повторное включение `auto_sync` при запланированной записи |
| NTP deadline | Ответ, наблюдаемый до таймаута, ровно на нём и после него; достижение секундной границы до и ровно на таймауте ожидания фронта |
| NTP second-edge window | Начало секунды, ровно 1 500 мкс и 1 501 мкс: последний случай должен ждать следующую секунду |

Оба NTP-таймаута имеют исключительную верхнюю границу: проверка/фронт ровно
на deadline уже не принимается. Эти тесты фиксируют границу текущего API,
а не считают её дефектом. Учитывается момент наблюдения ответа polling-циклом,
а не время прихода реального UDP-пакета.

В тестах raw ISR rollover ускоряется только начальное значение счётчика;
сами следующие фронты проходят через настоящий зарегистрированный обработчик.

При переполнении SQW-счётчика (≈136 лет при 1 Гц) фронт `0` пропускается,
следующий (`1`) читается штатно.

## Регрессии аудита проекта

Новые наборы выполняют настоящие `settings.cpp`, `handlers.cpp`,
`command_parser.cpp`, `touch.cpp`, `nus_service.cpp`, `event_isr.cpp`,
`event_dispatcher.cpp` и `event_timestamp.cpp`. В BLE-наборе задана контролируемая
конвертация ESP → UTC; форматирование и отправка метки выполняются прошивкой.
В тестах парсера выходом считается передача распознанного JSON в модель роутера.
В тестах конфигурации вызываются настоящие обработчики команд; неиспользуемые
обработчики удаляются линкером, их аппаратные зависимости не исполняются.

Проверки логов команд перехватывают аргументы всех уровней, включая DEBUG.
Проверяются маска `***` для пароля в `wifi` и `save_config` через BLE/Serial,
исходный пароль на входе обработчика, экранированные ключи/значения, фрагменты,
вложенные массивы, пустой пароль и отсутствие содержимого повреждённого ввода
в диагностике. Остальные поля команды должны сохраняться в логе.

NVS-модель сохраняет ключи между экземплярами менеджера и позволяет независимо
отказывать в записи выбранного ключа и очистке. BLE-модель задаёт результаты
`notify`, собирает доставленные байты и хранит RX StreamBuffer. Модель дисплея
фиксирует применённую калибровку и генерирует касания. Радиоканал, реальная flash,
доставка уведомления клиентскому приложению и параллельные задачи ESP32 не
моделируются. Заголовки ArduinoJson 7.4.3 с лицензией находятся в `vendor/`;
PlatformIO и сеть для запуска не требуются. Эта копия используется только host-тестами.

| ID | Проверяемое ожидание |
| --- | --- |
| AU001 | Wi-Fi, роль/номер, калибровка touch и политика синхронизации сохраняются после перезагрузки с заводским именем |
| AU002 | После отказа всех notify, частичной отправки START или отсутствия подписки событие доступно для последующей полной доставки |
| AU003 | При lost power/недопустимой дате RTC непрерывный настоящий SQW не сохраняет `RTC_OK` и не продлевает holdover бесконечно; оба режима `auto_sync` |
| AU004 | Ошибки записи String/bool/uint8/int16/uint16 и очистки NVS доходят до вызывающего кода; команды сообщают ошибку и не планируют reboot после неудачного reset |
| AU005 | Переподключение BLE очищает RX и peek; команда нового клиента не склеивается с оставшимися байтами предыдущего |
| AU006 | `save_config` немедленно применяет включение, выключение и калибровку touch |
| AU008 | После таймаута oversized-кадра первая корректная команда обрабатывается, в том числе при rollover `millis()` |

Контрольные сценарии проверяют обычное сохранение и сброс NVS, неизменённые
настройки без повторной записи, reboot для смены роли, штатные касания, BLE без
ошибок и с кратким backpressure, фрагментацию MTU, сборку JSON из фрагментов,
восстановление по newline/обычному таймауту и возврат доверенного RTC.

Запуск только новых областей:

```bash
python3 test/run_host_tests.py --sanitize --suite project
python3 test/run_host_tests.py --sanitize --suite rtc_trust_loss
```

`--suite` отбирает пути наборов до компиляции, `--filter` — имена сценариев.
Известные дефекты имеют маркеры `AUxxx`: обычный запуск допускает `XFAIL`,
а существующий CI с `--strict` завершится ошибкой, пока эти замечания актуальны.

## Результаты и исправление дефектов

- `PASS`: обычный тест прошёл.
- `FAIL`: обычный тест нарушил ожидание.
- `XFAIL`: известный дефект всё ещё воспроизводится.
- `XPASS`: тест известного дефекта прошёл; нужно проверить исправление и убрать
  его `known_issue` в таблице `kTests`, заменив ID на `-` (или убрав третий аргумент).
- `ERROR`: ошибка стенда, аварийное завершение или ошибка санитайзера.

Обычный запуск успешен при `PASS`/`XFAIL`; `FAIL`, `XPASS` и `ERROR` дают ненулевой
exit code. Чтобы считать известные дефекты ошибками запуска, используйте:

```bash
python3 test/run_host_tests.py --strict
```

Для работы над отдельным сценарием:

```bash
python3 test/run_host_tests.py --filter gps_replaces --strict
```

После исправления удалите замечание из списка известных дефектов, уберите его
маркер и сохраните тест как обычную регрессионную проверку. Новые сценарии добавляйте в соответствующий
набор, новые подсистемы — отдельными `*_test.cpp`. Аппаратные и интеграционные
тесты следует хранить отдельно от host-наборов.
