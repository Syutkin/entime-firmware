# Runtime operations notes

Дата: 2026-05-17

Этот документ фиксирует текущее эксплуатационное поведение прошивки.

## Maintenance-команды

Команды `sync_ntp` и `touch_calibrate` считаются ручными maintenance-операциями.
Во время их выполнения устройство не обязано надежно фиксировать стартовые или
финишные события.

Практический смысл:

- `sync_ntp` можно запускать перед работой, когда события не ожидаются;
- `touch_calibrate` также выполняется вне активного режима заезда;
- блокировка `loop()` во время этих ручных операций сейчас допустима;
- если потребуется использовать эти операции во время активной фиксации, их
  придется переводить в асинхронные state machine/job.

## BLE как основной канал

BLE NUS является основным каналом передачи событий. Поэтому отправку event
packets нельзя упрощать до best-effort/drop только ради того, чтобы быстрее
освободить `loop()`.

Если BLE notify испытывает backpressure, текущий `BleNusService::write()` может
ждать повторные попытки отправки. Это допустимо для сохранения приоритета BLE,
но влияет на latency основного цикла.

Неотправленный event packet сохраняется в RAM и повторяется из `loop()`.
Частичная отправка продолжается с оставшихся байтов; при новом подключении пакет
отправляется целиком. Другие записи NUS сначала завершают этот пакет. Пока он
ожидает отправки, следующий timestamp остаётся в single-slot ISR.

## Single-slot event ISR

Текущий `event_isr` хранит только один timestamp события. Если событие уже
захвачено и еще не обработано в `loop()`, следующий фронт игнорируется.

Это главный оставшийся риск в сочетании с BLE backpressure:

- BLE важен, поэтому нельзя просто дропать BLE event packet;
- но пока `loop()` занят отправкой, новый event timestamp может быть потерян;
- для START риск частично снижен фильтром `START_EVENT_DELAY_US`;
- для FINISH остается только ISR deadtime, поэтому запас меньше.

## Отложенный вариант улучшения

Когда будем возвращаться к этой теме, предпочтительный фикс:

- заменить single-slot ISR storage на кольцевой буфер timestamp событий;
- размер буфера начать с 8-16 событий;
- добавить overflow counter;
- отдавать overflow diagnostics в `status`;
- отправку по BLE оставить надежной, без silent drop для event packets.

Такой подход сохраняет BLE как основной канал и одновременно снижает риск
потери timestamp при временной блокировке main loop.
